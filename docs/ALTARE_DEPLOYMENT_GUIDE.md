# Cysle Egypt (TexLink) — Altare Production Deployment Guide

**Target Platform**: Altare App Hosting (`https://console.altare.gg/`)  
**Architecture**: Next.js 15 Standalone Container on Node.js 24 + Managed PostgreSQL 14+ + Persistent Object Storage  
**Application Branch**: `deploy/altare-production-prep`

## 2. Pre-Deployment Provisioning on Altare Console

Log in to the [Altare Console](https://console.altare.gg/):

### A. Provision Managed PostgreSQL
1. Navigate to **Databases** > **Create PostgreSQL Database**.
2. Select PostgreSQL version `15` or `16`.
3. Set database name: `cysle_egypt_prod`.
4. Note the connection details:
   - **Pooled Connection String** (PgBouncer port 6543): `DATABASE_URL`
   - **Direct Non-Pooling Connection String** (Port 5432): `DIRECT_URL` (Required for running Prisma migrations without transaction deadlock).

### B. Provision Persistent Object Storage
1. Navigate to **Storage** > **Create S3-Compatible Bucket** (or connect existing Supabase Storage).
2. Create two buckets:
   - `private-documents`: Restricted access, signed download tokens.
   - `public-assets`: Public read access for product photos and factory logos.

## 3. Environment Variables Configuration

In the Altare App settings under **Environment Variables**, configure the following keys:

| Variable | Requirement | Description / Format |
| :--- | :--- | :--- |
| `NODE_ENV` | **Required** | `production` |
| `PORT` | **Required** | `3000` |
| `DATABASE_URL` | **Required** | Pooled PostgreSQL connection string with `?schema=public&sslmode=require&pgbouncer=true` |
| `DIRECT_URL` | **Required** | Direct PostgreSQL connection string without pooler (port 5432) |
| `JWT_SECRET` | **Required** | Cryptographically secure random key (min 32 chars). Generate via `openssl rand -base64 32` |
| `NEXT_PUBLIC_APP_URL` | **Required** | Canonical domain (e.g. `https://cysle.eg` or `https://texlink.altare.app`) |
| `NEXT_PUBLIC_SUPABASE_URL` | Optional / Recommended | Supabase URL if utilizing Supabase Storage for media |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY`| Optional / Recommended | Supabase anonymous API key |
| `SUPABASE_SERVICE_ROLE_KEY` | Optional / Recommended | Supabase service role key for private document retrieval |
| `RESEND_API_KEY` | Optional | API key for transactional emails and notifications |

> [!CAUTION]
> In production, the application will refuse to start if `JWT_SECRET` is missing, shorter than 32 characters, or set to a known placeholder.

## 4. Build & Runtime Configuration

### Option 1: Dockerfile Deployment (Recommended)
Altare automatically detects the root `Dockerfile`:
- Base image: `node:24-slim`
- Multi-stage build (`deps` -> `builder` -> `runner`)
- Target executable: `server.js` generated by Next.js standalone output
- Non-root user: `nextjs` (UID 1001)

### Option 2: Native Altare Node Build
If deploying via native Node.js worker:
- **Node Version**: `24.x`
- **Build Command**: `npm run build:altare`
- **Start Command**: `npm run start` (or `node .next/standalone/server.js`)
- **Root Directory**: `.`

## 5. Production Database Migration Sequence

Before routing user traffic to a new version, run database migrations against the production database:

```bash
# 1. Verify connection status
npx prisma migrate status --schema=prisma/schema.postgresql.prisma

# 2. Deploy pending migrations safely (never drops data)
npx prisma migrate deploy --schema=prisma/schema.postgresql.prisma
```

> [!IMPORTANT]
> - Never run `prisma db push` in production.
> - Never run `npm run db:seed` in production. Destructive seeds are automatically blocked by the runtime guards.
> - If isolated synthetic demo accounts are required for platform testing, use:
>   `ALLOW_DEMO_SEED_PRODUCTION=true npm run db:seed:demo`

## 6. Healthcheck & Monitoring

- **Health Endpoint**: `GET /api/health`
- **Expected Status**: `200 OK`
- **Expected Payload**:
  ```json
  {
    "status": "healthy",
    "timestamp": "2026-11-24T03:30:00.000Z",
    "uptime": 120.5,
    "database": {
      "status": "connected",
      "latencyMs": 14
    },
    "environment": "production"
  }
  ```
- **Altare Healthcheck Probe**:
  - Path: `/api/health`
  - Interval: `15s`
  - Timeout: `5s`
  - Healthy Threshold: `2`
  - Unhealthy Threshold: `3`

## 7. Rollback & Disaster Recovery Procedures

1. **Instant Application Rollback**:
   In Altare Console, select **Deployments** > choose previous green deployment commit > click **Rollback**. Container images are preserved on registry and boot within seconds.
2. **Database Point-In-Time Recovery (PITR)**:
   Altare managed PostgreSQL maintains continuous WAL archiving. If a fatal data anomaly occurs, restore database state to a specific timestamp in the Altare Database dashboard.
